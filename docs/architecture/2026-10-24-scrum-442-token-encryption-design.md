# Provider OAuth tokens encrypted at rest (SCRUM-442): design

Status: spec, written from the code at `bcbb89a`. Nothing here is built.

## What this changes

The access and refresh tokens the gateway holds for a user's connected
services are stored encrypted, so a read of the live database alone yields
no usable token. The columns:
- `service_connections.access_token`, `refresh_token`;
- the legacy `plugin_connections.access_token`, `refresh_token`.

The key never enters the database. A token is decrypted only in the
functions that hand it to a provider or to a plugin.

The design choices:
- **AES-256-GCM with a key id.** Each value is encrypted directly under the
  current key, with a random 12-byte nonce for every write and the key's id
  written into the ciphertext. There is no wrapped per-row data key; a
  KMS-wrapped per-row data key is the upgrade if the key ever leaks.
- **One key** for every provider.
- **Rotation** is a re-encrypt command, not a schema change.

**The switch is invisible to users.** Nobody is logged out or asked to
reconnect at any step, including a rollback. Every step below holds this,
and the step that could break it (reads switching to the encrypted
columns) is gated so that it meets no row it cannot read.

Not in this ticket:
- the gateway's own access-token table and session cookie (SCRUM-443);
- Atlassian's refresh lock and revocation, and account deletion (SCRUM-444).

## What exists today (the code this builds on)

### The columns

`packages/db/src/schema/service-connections.ts` and `plugin-connections.ts`
declare `access_token text NOT NULL` and `refresh_token text`, written and
read as plain text.

### Every write

| Where | What it writes |
|---|---|
| `connected-accounts.ts` `upsertServiceAccount` (update and insert) | both tokens after a connect callback (Google, Atlassian, Notion) |
| `service-token.ts` `refreshGoogleToken` | the new access token |
| `service-token.ts` `refreshAtlassianToken` | the new access token and the rotated refresh token |
| `service-token.ts` `refreshNotionToken` (inside a `FOR UPDATE` transaction) | the new access token, and the rotated refresh token when Notion returns one |
| `app/api/servers/[slug]/connect/callback/route.ts` (update and insert) | the legacy `plugin_connections` pair |

### Every read

| Where | What it does with the token |
|---|---|
| `service-token.ts` `resolveServiceToken` (three selects: by account, default account, legacy fallback) | returns the access token; passes the refresh token to `REFRESH_FN` when expired |
| `service-token.ts` `refreshNotionToken` | compares the stored refresh token with the one presented, and may return the stored access token |
| `connected-accounts.ts` disconnect of one account, and `disconnectService` | reads both tokens and hands them to `revokeUpstream` |
| `mcp-server.ts` plugin dispatch (legacy path) | reads `plugin_connections.access_token` as the plugin's user token |
| `packages/db/src/backfill-connected-accounts.ts` | a one-off script from the multi-account migration; selects whole rows and uses the access tokens |

No other code selects these columns. There are no whole-row selects of either
table in the gateway, and no `returning()` of the token columns. A reconnect
overwrites the row's tokens and revokes nothing; only a disconnect revokes.

### The deploy path a new secret travels

1. An SSM SecureString in the production parameter store. The parameter's
   last path segment becomes the variable's name.
2. `scripts/render-env.sh` renders every parameter under the path into the
   host's env file.
3. `docker/docker-compose.prod.yml` passes only the variables it lists, so
   the new one must be listed.
4. `packages/config/src/index.ts` validates it. The gateway consumes that
   package as built `dist/`, so the package is rebuilt for the change to
   take effect.
5. `.env.example` and `docker/docker-compose.dev.yml` carry it for
   development.

### The image

The runtime image ships the gateway's `dist/` (built by `tsup` from
`server.ts`) and `.next`, with `apps/gateway` as its working directory. It
has no `tsx` and no source, so anything run in the container is a built
entry in `dist/`.

### Migrations

They are journaled SQL under `packages/db/drizzle/`, generated by
`drizzle-kit generate` and applied by `pnpm --filter @datatorag-mcp/db
db:migrate` from the repository root.

## Design

### 1. The sealed format

A token is stored as one text value:

```
v1.<key id>.<nonce, base64url>.<ciphertext and 16-byte tag, base64url>
```

- **Cipher.** AES-256-GCM with a random 12-byte nonce from `randomBytes`
  for every write, never derived and never reused.
- **AAD.** The additional authenticated data binds the value to where it
  belongs: `<table>.<column>:["<user_id>","<row_id>"]`, the pair written as
  JSON so no user id can run into a row id. A sealed value copied into
  another column, another table, another user's row, or another of the same
  user's rows fails to open, rather than serving a token to the wrong place.
  The row id is generated by the application before an insert (instead of
  by the database's default), so it is known at every write site.
- **Detection.** `sealedKeyId` returns the key id of a value in this form,
  and null for anything else.

### 2. The key

**One environment variable, `CONNECTION_TOKEN_KEYS`.**
- It holds a comma-separated list of `<key id>:<32 bytes, base64>`.
- The first key seals every new value; every key listed can open.
- A key id is `[a-z0-9]{1,16}`.

**Validated at start.** `packages/config` refuses to start the gateway if:
- the list is empty;
- any key is not exactly 32 bytes;
- an id repeats;
- the format is wrong.

The error names the variable and never prints a value.

**Creating it.** Manuel creates the production parameter himself, with the
key generated inline in the same command, so no session ever holds the
value and no command text contains it.

**Rotation.**
1. Add the new key first in the list.
2. Deploy.
3. Run the re-encrypt command (section 5), which re-seals every value under
   the first key.
4. Remove the old key from the list once no value carries its id.

No schema change, no downtime, nobody reconnects.

**Where it lives.**
- **Production:** an SSM SecureString beside the gateway's other secrets.
- **Development:** its own key, never the production one.
- **Tests:** a fixed test key, set in the test setup.

### 3. One module seals and opens

The module is `apps/gateway/src/gateway/token-crypto.ts`:
- `sealToken(value, { table, column, userId, rowId }): string`;
- `openToken(sealed, { table, column, userId, rowId }): string`;
- `sealedKeyId(sealed): string | null`.

**What it never does.** It never logs, and it never echoes a value in an
error. A value that will not open throws a fixed error naming the table and
column, never the value.

**Who may open.** Opening happens in `service-token.ts`, in the functions
that hand a token on:
- `resolveServiceToken`;
- the three refresh functions;
- `revokeUpstream`;
- a new `resolvePluginConnectionToken`.

The legacy `plugin_connections` read moves out of `mcp-server.ts` into
`resolvePluginConnectionToken`, so the dispatch never sees ciphertext or
plaintext from the table, only the token it passes on.

The one other module allowed to open is `token-crypto-commands.ts`, whose
re-encrypt and restore commands must (section 5). A test fails if any file
other than these two (tests excepted) imports `openToken`.

**Disconnects.** The two disconnect paths in `connected-accounts.ts` read
the sealed values and hand them to `revokeUpstream` unopened.
`revokeUpstream` opens them, so they are plaintext only inside the revoke
function. It gains the row context (user id and row id) it needs to open
them.

**The Notion refresh.** It compares the stored refresh token with the one
presented. With a fresh nonce on every write, two seals of one token never
compare equal, so it opens the stored value first and compares plaintext.
The same holds for the second, locked look in its `invalid_grant` path.

### 4. Migration order: production readable at every step

Expand, then contract, in three releases. Each production schema step is
confirmed by Manuel naming its target, under the schema-migration rule.

**`plugin_connections` is sealed-only from release 1.** It is the legacy
table, so it skips the dual write: release 1's migration adds its sealed
columns and drops `NOT NULL` from its plaintext ones, the callback writes
sealed values and null plaintext, and `resolvePluginConnectionToken` reads
sealed from the start. No backfill or restore covers it. The migration's
first statement raises if the table has any row, so it can never strand a
row with plaintext only; on a development database with legacy rows, they
are deleted first.

| Release | Schema | Code | Production reads | Rollback |
|---|---|---|---|---|
| 0. Key | none | none | plaintext | delete the parameter |
| 1. Expand | migration 1: add `access_token_sealed`, `refresh_token_sealed` (nullable) to both tables; drop `NOT NULL` on `plugin_connections.access_token` | `service_connections`: write both plaintext and sealed, read plaintext. `plugin_connections`: sealed only. The commands ship in this image. After the deploy, the backfill runs and must exit 0 | `service_connections` plaintext; `plugin_connections` sealed | previous image; the new columns are ignored, and a down migration drops them if wanted |
| 2. Read sealed | none | read the sealed columns and open them; still write both | sealed | release 1's image: it reads plaintext, which release 2 keeps writing |
| 3. Contract | migration A: drop `NOT NULL` on `service_connections.access_token`. Then, after a soak, migration B: a guard, then drop `access_token` and `refresh_token` from both tables | the schema no longer has the plaintext columns; reads and writes are sealed only | sealed | before B: release 2's image, plus the restore command, which rewrites every plaintext value from its sealed value so a further rollback to release 1 reads current tokens. After B: re-add the columns, run restore, then release 2's image. The key opens every row, so nothing is lost |

The sealed columns keep their `_sealed` names. Renaming them back would be a
second code change for no gain.

**Why release 3's image runs before migration B.** It does not reference
the plaintext columns, so it runs on the schema with them (nullable after
migration A) and without them. Between its deploy and B, an update leaves a
row's old plaintext in place; restore rewrites it if a rollback needs it,
and B removes it.

**The gate that keeps it invisible.** Release 2 refuses a row with no
sealed value rather than serving its plaintext: such a row would be a
defect, and a fallback would hide it. The backfill's exit code is what
guarantees no such row exists when release 2 ships:
- the backfill exits non-zero if, after its pass, any row has a plaintext
  token and no sealed one;
- release 1 seals every column it writes, so no column becomes unsealed
  after a backfill that exited 0;
- release 2 is deployed only after a backfill run that exited 0;
- migration B opens with a `DO` block that raises on the same count.

So the refusal is a zero-row case, not one a user meets.

### 5. Three commands, one module

These live in `apps/gateway/src/gateway/token-crypto-commands.ts`, run
through a small entry, `token-crypto-cli.ts`, which is a second `tsup`
entry built to `dist/tokens.js`, so the image carries it. HQ
runs it in the gateway container on the production host, on Manuel's
confirm naming the target:

```
docker compose --env-file <gateway env file> -f <gateway compose file> exec gateway node dist/tokens.js backfill
```

with the env and compose files the deploy skill names.

Each command:
- updates one row at a time, each `UPDATE` guarded so a concurrent write
  wins;
- is idempotent and resumable: a second run finds nothing to do;
- prints only counts.

| Command | Purpose | Guard |
|---|---|---|
| `backfill` | seals each plaintext value into its empty sealed column (`service_connections`), each column on its own | per column: `<column> IS NOT DISTINCT FROM <read value> AND <column>_sealed IS NULL`. Every write since release 1 that sets a column also sets its sealed column, so an empty one means no write to it since the read. A Google refresh writes only the access token, so a row can have one column sealed and not the other; taking each column on its own keeps that row from being skipped |
| `reencrypt` | opens and re-seals every value whose key id is not the current one (both tables) | the sealed value is still the one read |
| `restore` | rewrites plaintext from sealed values, for a rollback during release 3 (`service_connections`) | the sealed value is still the one read |

`backfill` and `reencrypt` are one loop with a different predicate.

**Why not a migration.** A journaled migration is SQL, and sealing needs the
key held by the application. Doing it in SQL (`pgcrypto`) would put the key
into a statement the database logs and keeps.

### 6. The one-off script

`packages/db/src/backfill-connected-accounts.ts` belongs to a migration that
finished long ago. It reads tokens as plain text, and it would break silently
after release 2. It is deleted in release 1, along with its entry in
`scripts/pattern-check.mjs`.

## What this achieves, and what it does not

**Achieves.** Once migration B has run, the live database holds no usable
provider token, and no user noticed the change.

**Does not achieve on its own.** Dropping the plaintext columns does not
remove values from copies taken earlier: the database's restore history
and any database branch copied from production before the drop. No step
forces a reconnect or rotates stored tokens, by decision, so those copies
stay usable until something ends them:
- **Restore history and pre-drop branches:** HQ deletes the branches copied
  before the drop and waits out the restore window. After that, no copy
  holds plaintext.
- **Atlassian:** Atlassian rotates the refresh token on each refresh, so a
  copied one stops working at the account's next refresh.
- **Notion:** the code stores the rotated refresh token Notion returns, so
  a copied one stops working at the next refresh if Notion invalidates the
  old token on rotation.
- **Google:** Google does not rotate refresh tokens, and a reconnect here
  revokes nothing, so a copied Google refresh token stays usable until the
  user disconnects (which revokes it), removes the app's access in their
  Google account, or Google expires it. Until the restore window has
  passed, these copies are the residual.

Access tokens in those copies expire within hours on their own.

## Tests

**`token-crypto.test.ts`:**
- A value round-trips.
- Two seals of one value differ.
- A tampered ciphertext, tag, nonce or key id does not open.
- A sealed value moved to another user, another row, table or column does
  not open.
- An unknown key id does not open.
- The first key seals and every listed key opens.
- `sealedKeyId` returns the id, and null for a value not in the format.
- An error never contains the value.

**Config tests:**
- A missing key, a short key, a duplicate id and a malformed list each
  refuse to start, naming the variable.

**One test per write site** (service-token, connected-accounts and the
plugin connect callback):
- what reaches the database is sealed, and opens to the token;
- in releases 1 and 2, the plaintext is written beside it in
  `service_connections`; `plugin_connections` gets null plaintext.

**Read and revoke paths:**
- `resolveServiceToken` and each refresh function hand the provider the
  opened token.
- The Notion refresh compares plaintext.
- `revokeUpstream` receives sealed values and opens them.

**Source rule:**
- A test fails if a file other than `service-token.ts` or
  `token-crypto-commands.ts` (tests excepted) imports `openToken`.

**Commands:**
- Each command is idempotent, guarded against a concurrent write, and
  prints no value. The backfill exits non-zero while an unsealed column
  remains, and exits 0 on a row a refresh sealed only half of.

**End to end,** before release 1's go: on a development database branch
that is not a copy of production, with a development key, the migration,
the backfill, a sealed read of a row whose plaintext was removed, and a
restore that gives back the original value. Only counts and the match are
recorded.

Every DB-backed test runs against the test database with a fixed test key.

## Decided by HQ

- One key for all providers.
- The migration runs under the schema-migration rule: Manuel confirms the
  SQL naming its target, and this session runs it.
- Nothing about the stored plaintext goes into a commit message or a
  changelog.
- The variable is named `CONNECTION_TOKEN_KEYS`.
- The three commands run in the container on the production host, by HQ,
  on Manuel's confirm naming the target: the same confirm-then-run shape as
  a migration. The product session never runs them.
- The switch is invisible to users: no forced reconnect and no rotation of
  stored refresh tokens as a step. The copies made before the drop are
  handled by HQ deleting pre-drop branches and waiting out the restore
  window.
