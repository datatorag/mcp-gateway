# Codebase Map

Architecture reference for the datatorag-mcp monorepo. Read this instead of re-exploring source. This repo is **public** — no live infrastructure values here; operational details (hosts, profiles, DB project ids) live in private memory (`reference_*` entries) and the `deploy` / `db-query` skills.

## Monorepo layout

pnpm workspace (`pnpm-workspace.yaml`: `apps/*` + `packages/*`), turbo topological builds (`turbo.json`: `build` depends on `^build`). All packages are private ESM built with tsup.

| Package | Role | Internal deps |
|---|---|---|
| `apps/gateway` | The whole product: Express + Next.js server — MCP gateway, OAuth server, marketing site, dashboard, cron jobs | auth, config, db, types |
| `packages/db` | Drizzle schema (15 tables, one file per table under `src/schema/`) + `createDb()` (`prepare: false` for Neon's pooled endpoint); dual exports `.` and `./schema` | none |
| `packages/config` | Single zod env schema; `getEnv()` memoized, `process.exit(1)` on invalid. `DATABASE_URL` is the only var without a default | none |
| `packages/auth` | `hashApiKey`, `safeStringEqual` (constant-time SHA-256 compare), `ApiKeyValidator` (LRU-cached). Consumed only by the OAuth routes | db |
| `packages/types` | zod status enums + `McpGatewayManifest` (the `datatorag.json` plugin manifest shape) | none |

(`packages/docker-manager` used to exist as dead code from the abandoned container-per-plugin design — it was deleted; see decisions.)

## Gateway request flow

```
MCP client
  │ POST /mcp  (Authorization: Bearer <OAuth access token>)
  ▼
apps/gateway/server.ts          validateBearer → oauthAccessTokens (not revoked/expired)
  │                             sessions: in-memory Map keyed by mcp-session-id
  │                             (wiped on every deploy — an unknown session id gets a
  │                             spec-compliant 404 via classifyMcpRequest (mcp-session.ts),
  │                             and clients silently re-initialize on the same bearer; SCRUM-23)
  ▼ new session → createMcpServer(userId, db, pool)
apps/gateway/src/gateway/mcp-server.ts
  │ ListTools: enabled tools ⋈ active mcpServers, filtered to the user's
  │           connected services ("lazy tool loading"); injects `account` param
  │ CallTool:  split tool name on "__" → serverSlug / toolName
  ▼
  ├─ service-mapped plugin → getServiceToken() → ONE-SHOT client,
  │                          token in X-User-Token header (never pooled)
  └─ generic plugin        → ConnectionPool (per-server, max 5, 5min idle,
                             5s acquire timeout, wait-queue)
  ▼ Streamable HTTP → http://<host>:<containerPort>/mcp
plugin child process            spawn("node", entrypoint), ports 40000+
                                managed by src/gateway/plugin-manager.ts
```

- **Auth** happens once per request at `server.ts` (Bearer lookup). Sessions live only in a process-local Map — a restart drops them all; clients must re-initialize.
- **Usage tracking**: every CallTool (success or throw) → `trackToolCall` (`track.ts`) → `classifyOutcome` (`usage/classify.ts`) → `writeUsageEvent` (`usage/write.ts`) racing the insert against a **200ms timeout** so metering never slows the response (events can silently drop). Nightly rollup to `usage_events_daily` + 90-day raw retention in `usage/rollup.ts`. Unmetered but still emitted: `gws_auth_*` tools (named in `NON_METERED_TOOLS`) and the gateway built-ins `echo`/`list_connected_accounts` (structurally, via `builtin: true` from the `BUILT_IN_TOOLS` registry dispatch in `mcp-server.ts` — SCRUM-66; before that they emitted nothing, a silent-emission defect since fixed). Both surfaces (`mcp`/`agent`) meter; thrown calls never do. Built-ins never claim `first_tool_call` activation; real plugin calls on either surface do (SCRUM-78). Agent-surface rows stamp `account_email` from the account the token resolution actually chose (the session's default), not the caller's stripped `account` argument — `resolveServiceToken` returns both halves.
- **Billing**: plans are binary `free`/`pro` (`payg` reserved for metered Stage 2; the trial plan was retired — the free tier IS the trial, and `users.plan` defaults to `free`). `src/gateway/billing/plans.ts` defines caps; `billing/enforce.ts` (`checkCallAllowance`) ENFORCES the free tier's hard stop in the CallTool path before dispatch — free = 250 calls hard cap, pro = 2,000 with no hard stop (metered overage is Stage 2, deliberately unbuilt). Internal accounts are exempt (`capExempt`). The AGENT-RUN allowance is PER PLAN in `planLimits()` (SCRUM-84: free 25/month, pro 100, unknown plans fall to free), bounded per run by `RUN_TOKEN_CEILING` (150k tokens, all plans) — enforcement in `mastra/run-token-budget.ts` refuses the run's NEXT model call at a step boundary and the chat route surfaces it as a user-visible product state, never truncating an in-flight call. This reversed the earlier plan-independent cap once the token ceiling was measured; pinned by tests in `plans.test.ts`, the chat route suite, and `run-token-budget.test.ts`. Stripe: `/api/billing/checkout` + `/api/billing/portal` (session-gated), `/api/stripe/webhook` (signature-verified, idempotent via the `stripe_events` claim table — see `billing/webhook-handlers.ts` for what each event does to `users.plan`).
- Cron jobs run in-process via node-cron, registered in `server.ts`: daily usage rollup (UTC), Slack digest, no-activation follow-up email (both America/Los_Angeles).

## Auth & OAuth flows

Three distinct flows — don't conflate them:

1. **MCP client OAuth** (`src/gateway/oauth/`): a full mini authorization server — `metadata.ts` (RFC 8414 authorization-server metadata, `/.well-known/oauth-authorization-server`) + `protected-resource.ts` (RFC 9728 protected-resource metadata at `/.well-known/oauth-protected-resource`, advertising the `/mcp` resource + this gateway as its authorization server; the `/mcp` 401s carry a `WWW-Authenticate: Bearer resource_metadata="…"` header pointing at it, with `error="invalid_token"` on a bad/expired token), `register.ts` (RFC 7591 dynamic registration; **public clients only** — always `token_endpoint_auth_method: "none"`, PKCE is the protection, no client secret is ever issued/verified), `authorize.ts` (redirects to Google; PKCE + client params round-trip through base64url `state`, which also carries a CSRF nonce matched against an httpOnly cookie at `/oauth/callback`; `redirect_uri` is re-validated against the registered client on callback), `token.ts` (PKCE-verified code grant → 24h access + 60d refresh token), `revoke.ts` (RFC 7009; also fires `onRevoked(userId)` so `server.ts` closes the user's live MCP sessions/SSE streams via `closeSessionsForUser` (mcp-session.ts) — DB-side revocation alone can't reach an already-open stream; still-authorized clients just re-init through the 404 path). Every `/oauth/*` endpoint is per-IP rate-limited (`rate-limit.ts`, mounted on the `/oauth` prefix in `server.ts`), keyed on the un-spoofable Cloudflare `CF-Connecting-IP` header — **not** `X-Forwarded-For` (Cloudflare appends to XFF, so its leftmost entry is client-forgeable) — falling back to the TCP peer when that header is absent. Prod sits behind Cloudflare (TLS terminates there; origin listens on `:80`). Refresh tokens rotate within a `familyId`; presenting an already-revoked token revokes the **whole family** (replay detection) **and its live access tokens** (`grants.ts` `revokeAccessTokensForClient`, scoped to `(userId, clientId)` so `"web"` sessions survive). Refresh lookup is row-locked (`.for("update")`) to serialize concurrent refreshes. Raw refresh tokens are never stored — only sha256 hashes. CSRF-nonce helpers live in `oauth/csrf.ts` (`nonceMatches` + shared TTL).
2. **Dashboard login** (`src/gateway/auth.ts`): `/auth/google` minimal-scope login → `users` row + 1-day session token (stored in `oauthAccessTokens` with `clientId: "web"`) set as httpOnly `dtrmcp_session` cookie. `src/proxy.ts` (Next middleware) gates `/dashboard/*` pages on that cookie, bouncing to `/auth/login?next=<path>`. **Where a login lands is decided in exactly one place**: `postLoginDestination` (`src/gateway/post-login-destination.ts`) — a four-case table (AGENT_DEFAULT_VIEW × new/returning; `signup=1` gates the Ads conversion, `welcome=1` makes an agent landing observable) with the requested `next` path as a case in FRONT of it (SCRUM-71). `next` travels login page → `/auth/google?next=` → short-lived httpOnly `dtr_next` cookie (survives Google's consent trip, same mechanism as attribution) → callback. It is validated INSIDE `postLoginDestination` (`resolveNextPath`: same-origin path only, reject-and-fall-back — an unvalidated post-login redirect is a phishing primitive), so a caller cannot forget the validation; don't add a second redirect site that bypasses this function.
3. **Service connections** (what plugins actually use): `/auth/google/connect` (full Workspace scopes) and `/auth/atlassian/connect`. Both resolve the user from the `dtrmcp_session` cookie and bind the round-trip with a CSRF nonce (a random value in an httpOnly cookie echoed via OAuth `state`) — the session token is **never** placed in `state`. Provider tokens land in `serviceConnections`; multi-account support layers `connectedAccounts` on top (with `isDefault`). `src/gateway/service-token.ts` resolves the per-user token at call time (`PLUGIN_SERVICE_MAP`: `gws-mcp` → `google-workspace`, `atlassian-mcp` → `atlassian`; anything else routes through legacy `pluginConnections`), refreshes expired tokens via `REFRESH_FN`, and — Atlassian only — persists the **new** refresh token, since Atlassian rotates it on every use. The resolved token is forwarded to the plugin as the `X-User-Token` header. **Scope-grant honesty (SCRUM-136)**: Google's consent screen lets a user untick individual scopes, so `src/gateway/scope-grant.ts` is the ONE place that compares a stored grant against `GWS_SCOPE_LIST` (which lives there; `auth.ts` joins it for the redirect) — it owns the alias table (Google stores `userinfo.email` long-form for our `email` request; naive comparison marks every FULL grant partial), the tool-prefix→scope map, and the worded messages. Consumers get the finished delta, never a scope array: the connect callback records `grant_complete`/`missing_scopes` on `account_connected` and appends `partial`/`missing` to the redirect; `/api/connections` returns `scopeStatus` per row; both call paths (`applyToolPolicy` agent-side, `mcp-server.ts` CallTool) pre-check the needed scope before dispatch (refusal metered with the `[missing-scope]` marker) and rewrite Google insufficient-scope 403s into words + a reconnect path — raw error in the usage row, words to the user. Everything fails OPEN (null/legacy scopes, unmapped tools like `gws_run`) — a wrong block refuses work the user could do; a miss just reproduces the old behaviour, caught by the 403 rewrite. **Per-service visibility (SCRUM-106)** sits on top: `serviceGrantStates` in the same module turns the delta into the per-service list (`{displayName, iconKey, granted}`, no scope URLs) that `/api/connections` ships as `scopeStatus.services`; `src/app/dashboard/connections/grant-state.ts` derives the ONE connection-level state (complete / partial / none / disconnected — per-service "partial" cannot exist, each service is one scope) that the card badge and `grant-panel.tsx` both render from; `GrantPanel` is the single component behind the connections page, the service detail page and the agent's in-thread card (compact, fed by `ConnectGrantContext` at render time, never stored in the `data-connect` part). All-declined renders one sentence and one reconnect anchor, never a row per service; raw scopes live only behind a closed `<details>`. It absorbed the SCRUM-136 one-line banner. **Zero-grant gate (SCRUM-149)**: SCRUM-136 was detection; this is prevention. The Google connect callback REFUSES a consent positively observed to cover zero services — `tokens.scope` present and `grantedServiceCount === 0` — writing neither `service_connections` nor `connected_accounts` (which also means a zero re-consent can never clobber a working grant), skipping the userinfo fetch, and redirecting with `error`/`connect_error=no_services_granted` (`CONNECT_ERROR_NO_SERVICES` in `post-connect-destination.ts`, the one exported spelling). `account_connected` does NOT fire for a refusal — `account_connect_refused` does (`trackConnectRefused`), so the funnel keeps its meaning and the drop-off stays measurable. Fail-open is untouched: a response with no scope field is stored exactly as before, and Atlassian (no per-scope opt-out) is never gated. Landing surfaces split zero from partial: the agent page picks words via `connectErrorNotice` (zero gets `CONNECT_ZERO_GRANT_NOTICE`, naming "Select all"); the dashboard renders `ConnectOutcomeNotice` with a retry anchor — possible only because the retired `/dashboard/connections` index now FORWARDS its query string (`connectionsForwardPath`) instead of dropping every outcome param on the fallback leg. Partial grants (at least one service) are stored and marked exactly as SCRUM-136 shipped. Pinned in `auth-connect-grant.test.ts`, both directions, mutation-proven. **Consent interstitial (SCRUM-150)**: the failure SCRUM-149 records happens on Google's screen, where we control nothing, so the only lever is the moment before the handoff — held at the CHOKE POINT, not on the controls: `GET /auth/google/connect` without `proceed=1` renders a self-contained Express instruction page (`connect-interstitial.ts`: boxes come unticked, "Select all" named, schematic illustration rather than a fake Google screenshot, light/dark via prefers-color-scheme) whose Continue link is the same route with `proceed=1` and the encoded `next` carried through; the proceed leg is byte-identical to the old flow, and nothing one-shot (nonce, attribution, next cookie) is stashed for a page view. Every connect surface — cards, detail page, agent in-thread card, docs links, the SCRUM-149 retry — passes through without knowing it exists. Atlassian deliberately has none (no per-scope opt-out). The full-scope request is pinned by test: the fix for consent drop-off is instruction, never silently narrowing the request (per HQ decision, see SCRUM-136/149). **Default-account rule (SCRUM-145)**: nothing used to move `is_default` after first connect, so a first identity-only consent kept the default forever and every argument-less call resolved to a grant that could serve nothing — the SCRUM-136 refusal then survived the user complying with it. Now `ensureUsableDefault` (`connected-accounts.ts`) runs after every `upsertServiceAccount`: a default covering at least one service is NEVER moved (a narrow default can be a deliberate choice), a default covering zero yields to the widest grant, tie-broken by most recent grant activity; `promoteNextDefault` ranks disconnect promotions the same way (usable first, then oldest). The ranking primitive is `grantedServiceCount` (`scope-grant.ts`), fail-open like the rest of that module — null/legacy scopes and non-Google connectors score as fully usable, so nothing can demote a connection the module cannot read. Deliberately NOT scope-aware per-call resolution: the account a call runs as must stay predictable, or a fixed read becomes a silent cross-account WRITE (the SCRUM-120 hazard). The other half is refusal honesty: when the pre-call gate refuses, both surfaces name the account they judged and any other connected account that does hold the scope (`accountsGrantingScope` + `missingScopeMessage`'s `accountEmail`/`alternates`; the agent wording steers to the default switch because the account argument is stripped on that surface, the MCP wording offers the `account` parameter). And the legacy no-`connected_accounts` fallback is ordered (widest scopes, then newest, then id) instead of heap order. Pinned end to end by `default-account.test.ts` (real Postgres, mutation-proven). **The user-facing control (SCRUM-147)**: MCP-surface scope refusals deep-link `/dashboard/connections/<service>` (the bare connections URL redirects to the overview, which used to be a page WITHOUT the switch), and both account-list surfaces render `SetDefaultControl` + `BetterDefaultSuggestion` from `src/app/dashboard/connections/default-control.tsx` — one shared control, two-step in-flow confirmation naming the consequence (never a popover: dashboard `main` clips inline floating elements), server re-fetch on success, never optimistic. `suggestBetterDefault` (`grant-state.ts`) is the UI mirror of the server rule: suggest only off a zero-grant default toward a RECORDED complete sibling. A single-account user gets no switch control at all — their remedy is the GrantPanel reconnect, not a disabled button. And a null-scope row on the audit surface says `GRANT_UNRECORDED` instead of "Every service was granted": fail-open "complete" is policy, not a reading, and must not become a positive claim. Both connect flows honour a validated `?next=` (SCRUM-78): parked in the httpOnly `dtr_connect_next` cookie for the round trip, composed and re-validated in `postConnectDestination` (`src/gateway/post-connect-destination.ts`, same reject-and-fall-back discipline as `postLoginDestination`, including re-validating the COMPOSED path), landing back on the requested path with `connected=<provider>` or `connect_error=<code>` appended — the mechanism that returns the agent's inline connect control to its thread. That file also records the popup-vs-redirect decision; the fallback destinations are byte-identical to the old hardcoded connections-page redirects.

## Site & content systems

- **Blog / changelog / docs are markdown-in-repo**, not a CMS: content in `apps/gateway/content/{blog,changelog,docs}/*.md`, parsed by three near-identical hand-rolled parsers `src/lib/{blog,changelog,docs}.ts` (gray-matter + `marked.parse`, no MDX). Each keeps a module-level cache populated once per process — content changes need a restart/redeploy to appear.
- **Frontmatter contracts** — field-by-field tables with fallbacks live in the `site-content` skill. Headline facts only: blog `readTime` is computed from word count (not frontmatter); changelog `connector` is convention-only, unvalidated; docs `connector` (not `section`) drives sidebar grouping via `src/lib/docs-connectors.ts` `CONNECTORS` registry — URLs stay flat, e.g. `/docs/gmail`.
- **`/tools/[slug]` is DB-driven**, not markdown: queries `mcpServers`/`tools` directly, 404s unless `status === "active"`, renders the plugin README from the local plugin dir first, then GitHub API fallback (1h revalidate). Home page integrations grid also queries the DB directly.
- **App-router conventions**: no Navbar in root layout — every top-level page renders its own `<Navbar />`; `/docs` and `/dashboard` have their own nested layouts (no Navbar). `components/navbar.tsx` `flatItems` is the single source for desktop + mobile nav. Shipping a new top-level route = page + `flatItems` entry + footer link in `app/page.tsx` (no lint enforces this). Blog/docs use `generateStaticParams`; dashboard pages fetch client-side from rate-limited `/api/usage/*` routes (via `src/lib/with-route.ts` — session auth + rate limit + generic-500 catch-all; every session-gated JSON route uses it).
- **ONE shell for every `/dashboard/*` route; only the CONTENT mode differs.** `dashboard/layout.tsx` renders one icon-only 56px rail on all of `/dashboard/*` (labels live in `aria-label`/`title`, active state in `aria-current`), inside a shell that is ALWAYS the measured space below the top chrome and ALWAYS `overflow-hidden`. **The document never scrolls on a dashboard route — `main` does.** The `FULL_HEIGHT_ROUTES` set (`/dashboard/agent` today) now decides exactly one thing: a route in it gets `children` with NO padded `max-w-5xl` wrapper and `main` set to `overflow-hidden` so the surface manages its own scrolling region; every other route gets the padded wrapper and `overflow-auto` on `main`. Before editing: a full-height page must not add page padding or a heading of its own; the rail deliberately is not a scroll container (`overflow-y-auto` forces `overflow-x` to auto and clips the user-menu popup, which is wider than the rail); and because the scroll lives on `main`, the layout resets `main.scrollTop` on `pathname` change — the browser only does that for free when the DOCUMENT scrolls, and this layout stays mounted across dashboard routes. If you add a third thing to the `fullHeight` branch, stop: two separate production defects came from that branch growing. Guarded by `src/app/shell-invariants.test.ts`. **One consequence to know about: `main` now genuinely clips**, because the shell finally has a definite height for it to clip against — the `overflow-auto` there was inert before. Today's dialogs and sheets are portaled and the user menu sits outside `main`, so nothing is affected, but any NEW popover, dropdown or confirm affordance rendered inline inside a dashboard page must be portaled or it will be cut off at the content box instead of overflowing visibly. That would matter most for an approval prompt, which is exactly the kind of control that must never be half-visible.
- **A full-height shell is NOT `h-dvh`, and this has bitten twice.** `useFitBelowTopChrome` (`src/lib/use-fit-below-top-chrome.ts`) measures the shell's own top edge and sets `height = innerHeight - top`. The reason: the marketing page loads a third-party badge widget whose fixed bar AND compensating `body { padding-top }` both deliberately survive client-side navigation, so anyone arriving from the marketing site carries an offset into the app. A `dvh` shell then keeps a full viewport height, starts lower, and pushes its bottom — and the composer anchored there — off screen by exactly the offset. A direct load has no widget and no defect, which is why route-loading checks miss it entirely: **reproduce this by navigating from `/`, never by loading `/dashboard/agent` directly.** Do not "simplify" the measurement to a constant or to `body` padding: the widget has a second, in-flow variant on iOS Safari with no padding at all. Anything inside the shell that wants full height must use `h-full` (which tracks the measured value), never `dvh` — an aside asking for `dvh` becomes taller than its own parent and gets clipped at the bottom, where the user menu lives. **The measurement now runs on EVERY dashboard route, and the aside is `h-full` on every route.** An earlier version of this bullet said the opposite — that the rule was full-height-only and the two-branch aside height "is correct; do not simplify it to one" — and that was documentation preserving a bug as an invariant. Scoping the measurement to one route meant everyone arriving from the marketing site got a shell 36px taller than the space left, on every OTHER route: measured logo at 91 on the scrolling routes against 55 on `/dashboard/agent`, the shell bottom 36px below the fold, and sign-out unreachable. Making the shell a definite height everywhere removes the `min-h-screen` premise the two-branch rule rested on. The rail itself is now EXPANDABLE (SCRUM-83): a toggle button under the logo flips it between the icon rail and a labelled column, state persists across navigation (the layout stays mounted) and reloads (localStorage), and the width flips instantly rather than animating — the aside must stay `overflow-visible` for the user-menu popup, so a width tween would spill the nowrap labels over `main`.
- **One layer owns the anti-framing headers, and it is Express.** `securityHeaders` (`src/gateway/security-headers.ts`) sets `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` on EVERY response, mounted as the first `app.use` in `server.ts`. Do not add a second source at Cloudflare or in `next.config`: `setHeader` REPLACES rather than merges, so a CSP added elsewhere for scripts would silently drop `frame-ancestors` with no error anywhere, and two authorities disagreeing is the durable defect even when the pick happens to be right. If a CSP is ever genuinely needed for scripts, extend the one in this module rather than adding a competing one; a test asserts `next.config` does not set a CSP that omits `frame-ancestors`. **Verifying this needs BOTH a cache-busted header read AND a real framing attempt** — a header read is the "process is alive" shape of check. The framing probe must have a known-frameable control and must require the browser to POSITIVELY attest the block (an attributed `frame-ancestors` console message), because a frame that merely failed to load leaves an identical empty frame tree, which reads as protection and is not.
- **`overflow-x: clip`, NEVER `hidden`, on `html` and `body`.** `hidden` makes the element a scroll container, and then every `position: sticky` DESCENDANT pins to that element's scrollport instead of the viewport. Since `body` itself never scrolls (the viewport does), those elements silently stop sticking and travel with the page — no error, no warning, and it looks fine until you scroll. This shipped: `body` carried `overflow-x-hidden` while `globals.css` correctly used `clip` on `html` **with a comment explaining exactly this**, so the reasoning existed one file away and was never carried across. It broke the dashboard rail and the `/docs` sidebar, and the docs one went unreported for as long as it existed. `clip` gives identical clipping with no scroll container. Both are pinned in `src/app/shell-invariants.test.ts`, but note what that test can and cannot do: jsdom has no layout, so it asserts the class STRINGS and nothing else — the behaviour has to be checked in a real browser (scroll the page, read the sidebar's `getBoundingClientRect().top`; broken gives you exactly `-scrollY`).
- **`.prose` typography is hand-rolled** in `src/app/globals.css` — not `@tailwindcss/typography`. No `img` rule; code-block colors are hardcoded hex (duplicated in `tools/[slug]/page.tsx`).

## Key decisions

Big architectural decisions get an ADR page in `docs/architecture/decisions/`
(template there; company decision log lives in the private hq repo). This table is
the quick reference; the ADRs carry context + alternatives-considered.

| Decision | Why | Evidence |
|---|---|---|
| File-based markdown content (blog/changelog/docs) vs DB; `/tools` pages DB-driven | Content is static at deploy time — parse once, cache in-process; tool pages must reflect live plugin registry | `apps/gateway/src/lib/blog.ts` cache comments; commits `5c7f04f`, `f67a24d` |
| Neon serverless Postgres for prod, not docker postgres on the host | Managed DB; prod gateway decoupled from `db-init` so migrations can't block startup; `prepare: false` required for Neon's PgBouncer pooling | commit `a4e56b3`; `packages/db/src/index.ts` |
| Plugins run as host child processes (`spawn`), NOT Docker containers | Simpler than the original container-per-plugin design; the never-imported `packages/docker-manager` vestige was deleted, but the `containerPort` column name still reflects the abandoned model | commit `c9b77f3`; `apps/gateway/src/gateway/plugin-manager.ts` |
| Meta-tool gateway migration: decided direction, **deliberately not executed yet** | Direct tool exposure (~60 tools) is faster/simpler; migrate when catalog crosses ~100 tools. Meanwhile: self-contained tool descriptions, no runtime dependence on the `__` prefix | `docs/architecture/2026-04-22-meta-tool-migration.md` |
| Public POST/DELETE `/api/servers` endpoints removed; plugin installs now via SSH on the host | Unauthenticated plugin management on a public gateway was a security hole | commits `7fb0356`, `f8a6c4f` |
| Per-user-token plugin calls bypass the pool with a one-shot client | Avoids per-user pooling complexity while guaranteeing the right `X-User-Token`; pool stays credential-free | commit `fe083e2`; `user-tools.ts` (`callPluginToolOnce`, consumed by `mcp-server.ts` + playground) |
| `execFileSync` (never `execSync`) for git clone / installs | Prevents shell injection via malicious `githubRepoUrl` | commit `70cc29a` |
| Constant-time compares (`safeStringEqual`) for all PKCE/client_id/redirect_uri checks | CASA Tier 2 SAQ item; part of the passed Google CASA evidence trail | commit `0bbfd7f`; `packages/auth/src/index.ts` |
| **Anti-framing headers are owned by the ORIGIN, in Express — not Cloudflare, not `next.config`** | The dashboard renders tool-approval prompts, so framing protection is load-bearing, and a guard that lives in an edge dashboard does not travel with a clone, cannot be tested, and is invisible to a diff. Express is also the only true choke point: it fronts both the Next routes and the `/mcp`, `/oauth`, `/auth` and `/health` routers, so one `app.use` covers everything with no per-route question to get wrong | `src/gateway/security-headers.ts`, mounted first in `server.ts`; `src/gateway/security-headers.test.ts` |
| Lazy tool loading: ListTools filters by connected services | Keeps the advertised tool list honest about what the user can actually call | commit `d2d45ee` |
| Slack via `chat.postMessage` bot token, not webhooks | Reuses the existing "Dara" Slack app; one token + channel-id env vars instead of three webhook URLs | commit `a426a0a`; `src/lib/slack.ts` |

## Invariants & gotchas

- **Two same-named `plugin-manager.ts` files**: `apps/gateway/src/lib/plugin-manager.ts` is the 22-line `getPluginManager()` singleton accessor (globalThis-based for Next hot-reload); `apps/gateway/src/gateway/plugin-manager.ts` is the actual 500-line `PluginManager` class. Easy to open the wrong one.
- **`startAll()` does not re-discover tools** — it only respawns processes for `status: "active"` servers. `discoverTools()` runs only during install/reinstall. A plugin whose tool set changed needs a reinstall, not a gateway restart.
- **`discoverTools()` deletes all `tools` rows for a server, then reinserts** — and `tools.enabled` defaults `true` (`packages/db/src/schema/tools.ts`), so reinstalling a plugin resets any manually-disabled tool to enabled. Mid-reinstall, ListTools can briefly see an empty tool set for that server.
- **`/api/servers` is session-auth-gated** (GET included); the public POST/DELETE install/uninstall endpoints no longer exist. Plugin reinstalls require SSH to the gateway host (see the `deploy` skill).
- **Dev server port comes from the root `.env`** (`GATEWAY_PORT`) — `pnpm dev` runs `node --env-file=../../.env`. It is NOT Next's default 3000 (dev compose publishes 8285).
- **The free-tier call cap IS enforced now** — `checkCallAllowance` (`billing/enforce.ts`) gates plugin-tool dispatch in `mcp-server.ts` (built-ins deliberately keep answering for a capped user). A blocked call is an `isError` result, never dispatched, never metered. `planLimits` treats an unknown runtime plan value as free limits (least privilege), never a crash.
- **MCP sessions are in-memory only** — every deploy/restart drops all live client sessions.
- **`ConnectionPool` is per-server, shared across all users** — it must never carry a per-user credential; that's the whole reason for the one-shot-client bypass. Preserve this split when touching plugin call paths.
- **Date rendering convention**: always parse `YYYY-MM-DD` frontmatter dates as `new Date(\`${date}T00:00:00\`)` (never bare `new Date(date)`, which is UTC midnight and shows the previous day west of UTC). Changelog, blog listing, and blog post pages all follow this now — keep any new date-rendering page consistent.
- **Migration `0004` numbering collision** in `packages/db/drizzle/`: hand-written `0004_leads.sql` (outside drizzle's journal) coexists with drizzle-generated `0004_smiling_hercules.sql` (in the journal). The only documentation is a SQL comment at the top of `0004_smiling_hercules.sql`. Be careful interpreting `drizzle-kit generate` diffs around the `leads` table.
- **`getEnv()` hard-exits on invalid env** (`process.exit(1)`), at first call — not import — so a bad `DATABASE_URL` can kill the process mid-request-path rather than at boot.
- **Dev compose doesn't forward Slack/Brevo/PostHog-server vars** into the container (prod compose does) — those features silently no-op in dev even with the var in `.env`. Empty `SLACK_BOT_TOKEN`/`BREVO_API_KEY` = intentional logged no-op, not a bug. Stripe is the exception: `getStripe()` throws on a missing key.
- **Usage metering is best-effort** (200ms insert timeout) — anything built on `usage_events` must tolerate undercounting. Stored error messages are PII-scrubbed by `usage/redact.ts` (emails, long IDs) — expect `[redacted-*]` artifacts.
- **`__` is the load-bearing tool-name separator** (`NAMESPACE_SEPARATOR`): CallTool splits on the first occurrence. A slug or tool name containing `__` misroutes.
- **Server-side events cannot be attributed without a session id** — a `posthog-node` capture carries none of its own, so it can't be joined to the browsing session that produced it. New server-side events that need to be attributable must spread `sessionProps()` (`src/lib/attribution.ts`); new auth-redirect routes must be added to `ATTRIBUTED_PATHS` in `src/components/attribution-links.tsx` and must `stashAttribution`/`takeAttribution` across the provider round-trip. The session id is read at click time, never cached at mount (sessions roll over on idle timeout and at UTC midnight — a cached one is confidently wrong and nothing flags it). Full pattern in the `services-integrations` skill.
- **Never-throw convention** for side channels: `sendSlack`, `brevoPost`, all analytics/track functions catch internally and warn with a `[module]` log prefix. Exactly-once side effects use atomic `UPDATE … WHERE <flag> IS NULL RETURNING id` claims (`first_tool_call_at`, follow-up emails).
- **Content parser caches never invalidate** — editing markdown does nothing on a running prod server; redeploy.
- **Both surfaces meter AND both can claim activation** — two reversals, in order: the `agent-metering` branch made the agent surface write `usage_events` (it used to write none), and SCRUM-78 widened `first_tool_call_at` to claim on a successful non-builtin plugin call from EITHER surface (it used to be `surface: "mcp"` only). The widening was deliberate: the agent is the activation front door, and the inline-connect flow is measured by exactly this metric — an mcp-only gate was structurally blind to it. The `first_tool_call` event now carries `surface`, so the narrower "own MCP client" cohort stays one filter away; the no-activation email correctly stops nagging users whose agent already did real work. Built-ins and introspection tools still never claim it. Both surfaces emit one `tool_call` event carrying `surface` (`"mcp" | "agent"`). The per-period run allowance lives in `src/gateway/usage/period.ts` (details in the `services-integrations` skill's Playground section).
- **Playground writes are user-gated, fail-closed** — the Mastra agent runtime pauses for approval on any tool whose `requireApproval` is true, and that flag is set from `classifyWrite` (`playground/tools.ts`) in `src/mastra/mcp/client.ts`. Classification is decided from the tool's NAME and source-resident lists only — the MCP `readOnlyHint` annotation is deliberately NOT consulted (a server could mark a destructive tool read-only and walk past the prompt; that path was deleted with the Mastra rebuild). Decision order: `ALWAYS_WRITE_TOOLS` escalation → write-verb token floor (`isWriteTool`, raise-only, nothing can dig under it) → `KNOWN_READ_TOOLS` allowlist (the reviewed set of tools that run unprompted) → default WRITE (unrecognised names fail closed and prompt). **Shipping a new tool therefore requires classifying it in the same commit**: add it to the snapshot in `playground/tool-classification.test.ts` and, if it's a read, to `KNOWN_READ_TOOLS` — a test asserts those two lists agree, and a DB-backed test (runs when `DATABASE_URL` is present; vitest.config seeds it from the root `.env`) asserts the snapshot covers the live registry. A missing entry doesn't create a security hole, it creates an unnecessary approval prompt.
- **`connection-tester.tsx` and `setup-wizard.tsx` are both GONE** — the connection tester was absorbed into the setup wizard, and the wizard was then split (SCRUM-118/122): the client picker + config snippets live in the shared `SetupInstructions` component, and the live `/api/setup/status` poller lives in `src/app/dashboard/mcp-config/connection-status.tsx`, both rendered by the `/dashboard/mcp-config` page. Old references to either file mean that page now.
- **Relative imports in `apps/gateway` are extensionless** (`from "../lib/slack"`, never `"../lib/slack.js"`). tsconfig `moduleResolution: "bundler"` makes extensionless valid for every consumer — tsc, the tsx dev runtime, tsup, Next's webpack prod build, AND Turbopack (`pnpm dev`). `.js`-suffixed relative specifiers were normalized away after they broke the Turbopack dev server for any app route transitively importing `gateway/*.ts` (a webpack-only `extensionAlias` workaround existed briefly and was removed — webpack's hook doesn't apply to Turbopack, so it fixed prod while dev stayed broken). Package-subpath imports keep their extensions (e.g. `@modelcontextprotocol/sdk/client/index.js`). Don't reintroduce `.js` relative specifiers.
- **The testcontainers harness is live** — `src/test-utils/db.ts` (real Postgres via `@testcontainers/postgresql`, runs drizzle migrations) has a real consumer: `src/app/api/setup/status/route.liveness.test.ts`. Suites using it must gate on `isDockerAvailable()` (`describe.skipIf`, probed synchronously at import time) so `pnpm vitest run` still passes on machines/CI without a Docker daemon — and must never call `getTestDb()` at module-import time, only inside the gated block's `beforeAll`.

## Quality pass — design-time, not post-hoc

Do NOT run agent-fan-out review passes (`/simplify`-style, 4 parallel agents) on
every change by default — that burns tokens re-discovering what a 60-second
design check catches up front. Instead, before implementing, answer these four
questions inline (in the plan or in your head, one grep each) and let the
answers shape the code:

1. **Reuse** — does a helper for this already exist? Grep shared modules
   (`response.ts` in gws-mcp, `src/lib/` + `src/gateway/usage/` here) and the
   file you're editing's neighbors before writing a new one. If you find a
   near-match, promote it to the shared module rather than copying it.
2. **Source of truth** — if the change displays or derives data that exists
   elsewhere (docs frontmatter, DB, a registry), read it from there; never
   hand-copy values that will drift.
3. **Altitude** — is this a special case layered on shared infrastructure? If
   the same problem exists for sibling tools/routes, fix the shared layer once.
4. **Efficiency** — anything hot-path, per-request, or per-item that could be
   hoisted, batched, or skipped early?

Reserve the agent fan-out review for when the user asks for it, or for large
multi-file changes where a fresh-eyes sweep genuinely pays for itself.

Once a diff already exists, the `pattern-review` skill is the post-hoc form of
the same four questions — one pass, scoped to the diff, no fan-out. It runs
`scripts/pattern-check.mjs` (deterministic rules, self-tested, exit 0/1/2) before
spending any model judgement, and it proposes rather than rewrites. It does not
restate this map; it consumes it. The rule above is unchanged: the design-time
check is still the cheap one, and reaching for the review pass on every small
edit means the design-time check was skipped.

- Dev: `pnpm dev:gateway`; or in `apps/gateway`: `pnpm dev`. There is no local postgres — `DATABASE_URL` points at a Neon branch, and nothing migrates on boot.
- Migrations: `pnpm --filter @datatorag-mcp/db db:generate` / `db:migrate` (`db:push` is dev-only)
- Deploys and DB queries: use the `deploy` and `db-query` skills — infra specifics live there and in private memory.
